This tutorial shows you how to stream a Kafka topic into a hypertable with the Debezium JDBC sink connector, tune the connector's batch size, and stop and restart the connector partway through a load with no duplicate rows. It uses a sample manufacturing dataset that has hourly readings from ten sensors on each of five factory machines, over ten years, with about 4.4 million records in total.

If you want an overview of streaming Kafka topics into Tiger Cloud first, see [Integrate Apache Kafka with Tiger Cloud](https://www.tigerdata.com/docs/integrate/data-ingestion-streaming/apache-kafka).

## What you learn

- How to configure a JDBC sink connector to upsert into a hypertable on a composite key.
- Why the hypertable's time column takes the event's own timestamp.
- How `batch.size` and `max.poll.records` affect ingest throughput.
- How a restarted connector replays events without duplicating rows.

```bash
export DATABASE_URL="<connection string>"
psql "$DATABASE_URL"
```

</NumberedItem>
<NumberedItem title="Create the hypertable">

Create the `sensor_data` hypertable with [`CREATE TABLE ... WITH`](https://www.tigerdata.com/docs/reference/timescaledb/hypertables/create_table) by running this SQL in your `psql` session:

```sql
CREATE TABLE sensor_data (
    time        timestamptz NOT NULL,
    device_id   text NOT NULL,
    tag         text NOT NULL,
    value       double precision,
    unit        text,
    description text,
    ingested_at timestamptz NOT NULL DEFAULT now()
) WITH (
    tsdb.hypertable,
    tsdb.partition_column = 'time',
    tsdb.chunk_interval = '7 days',
    tsdb.columnstore = false
);
```

The connector leaves `ingested_at` unset, so the column records when each row arrives in the database.

</NumberedItem>
<NumberedItem title="Add a unique index">

Add a unique index on `device_id`, `tag`, and `time` by running this SQL:

```sql
CREATE UNIQUE INDEX sensor_data_device_tag_time_idx
    ON sensor_data (device_id, tag, time);
```

The connector's upsert needs a unique index on exactly the columns that identify a reading. A unique index on a hypertable has to include the partitioning column, which is `time` in this table. For more detail, see [Primary keys, time columns, and uniqueness](https://www.tigerdata.com/docs/learn/data-model/primary-keys-time-and-uniqueness).

</NumberedItem>

Run every shell command in this tutorial from this directory. Keep the `psql` session open in the first terminal for the SQL.

## Publish the readings

<NumberedList>
<NumberedItem title="Write the producer script">

Install [`confluent-kafka`](https://pypi.org/project/confluent-kafka/), the Kafka client for Python, by running this command:

```bash
pip install confluent-kafka
```

Save this script as `produce.py`:

```python
"""
Publish manufacturing.csv to the sensor_data Kafka topic.

Each row becomes one JSON event that carries its schema and has the
machine's device_id as its key.
"""
import csv
import json
import sys
from pathlib import Path

from confluent_kafka import Producer

CSV_PATH = Path(__file__).resolve().parent / "manufacturing.csv"
TOPIC = "sensor_data"
SCHEMA = {
    "type": "struct",
    "optional": False,
    "fields": [
        {"field": "time", "type": "string", "optional": False,
         "name": "io.debezium.time.ZonedTimestamp", "version": 1},
        {"field": "device_id", "type": "string", "optional": False},
        {"field": "tag", "type": "string", "optional": False},
        {"field": "value", "type": "double", "optional": True},
        {"field": "unit", "type": "string", "optional": True},
        {"field": "description", "type": "string", "optional": True},
    ],
}

failed = 0


def on_delivery(err, msg):
    global failed
    if err is not None:
        failed += 1


def main():
    if not CSV_PATH.exists():
        sys.exit(f"Can't find {CSV_PATH}. Unzip manufacturing.zip first.")

    producer = Producer({
        "bootstrap.servers": "localhost:9092",
        "compression.type": "lz4",
        "linger.ms": 100,
        "on_delivery": on_delivery,
    })

    sent = 0
    with CSV_PATH.open(newline="", encoding="utf-8") as f:
        for row in csv.DictReader(f):
            row["value"] = float(row["value"])
            event = json.dumps({"schema": SCHEMA, "payload": row})
            while True:
                try:
                    producer.produce(TOPIC, key=row["device_id"], value=event)
                    break
                except BufferError:
                    producer.poll(0.5)
            producer.poll(0)
            sent += 1
            if sent % 500_000 == 0:
                print(f"Sent {sent:,} events...")

    producer.flush()
    if failed:
        sys.exit(f"Kafka rejected {failed:,} of {sent:,} events.")
    print(f"Published {sent:,} events to {TOPIC}.")


if __name__ == "__main__":
    main()
```

Each event has a `schema` part and a `payload` part. The connector reads the type of each field from `schema`, and the name `io.debezium.time.ZonedTimestamp` tells it that `time` is a timestamp with a time zone. The `time` field carries the timestamp the sensor recorded, taken from the file.

## Create the sink connector

<NumberedList>
<NumberedItem title="Write the connector configuration">

Save this file as `sink.json`, and replace `<host>`, `<port>`, and `<password>` with the values from your connection string:

```json
{
    "connector.class": "io.debezium.connector.jdbc.JdbcSinkConnector",
    "topics": "sensor_data",
    "connection.url": "jdbc:postgresql://<host>:<port>/tsdb?sslmode=require",
    "connection.username": "tsdbadmin",
    "connection.password": "<password>",
    "key.converter": "org.apache.kafka.connect.storage.StringConverter",
    "value.converter": "org.apache.kafka.connect.json.JsonConverter",
    "value.converter.schemas.enable": "true",
    "insert.mode": "upsert",
    "primary.key.mode": "record_value",
    "primary.key.fields": "device_id,tag,time",
    "batch.size": "500",
    "consumer.override.max.poll.records": "500"
}
```

With `insert.mode` set to `upsert`, the [Debezium JDBC sink connector](https://debezium.io/documentation/reference/stable/connectors/jdbc.html) writes every event as an [`INSERT ... ON CONFLICT ... DO UPDATE`](https://www.postgresql.org/docs/current/sql-insert.html) statement. `primary.key.mode` and `primary.key.fields` take the conflict columns from the event's value, and those columns match the unique index on `sensor_data`. `batch.size` and `consumer.override.max.poll.records` are both at their default of 500.

</NumberedItem>
<NumberedItem title="Register the connector">

Register the connector as `sensor-data-sink` through the Kafka Connect REST API by running this command:

```bash
curl -s -X PUT -H "Content-Type: application/json" \
    -d @sink.json \
    http://localhost:8083/connectors/sensor-data-sink/config
```

Check the state of the connector and its task by running this command:

```bash
curl -s http://localhost:8083/connectors/sensor-data-sink/status
```

Verify the output shows `RUNNING` for the connector and for its task. If `tasks` is empty, run the command again after a few seconds.

```
{"name":"sensor-data-sink","connector":{"state":"RUNNING","worker_id":"172.18.0.3:8083","version":"3.7.1.Final"},"tasks":[{"id":0,"state":"RUNNING","worker_id":"172.18.0.3:8083","version":"3.7.1.Final"}],"type":"sink"}
```

</NumberedItem>
<NumberedItem title="Measure rows per second at the default batch size">

Create a view that measures the ingest rate, then query it, by running this SQL in your `psql` session:

```sql
CREATE VIEW ingest_rate AS
SELECT count(*) AS rows,
       count(*) / NULLIF(count(DISTINCT ingested_at), 0)
           AS rows_per_batch,
       round(count(*) / NULLIF(extract(epoch FROM
           max(ingested_at) - min(ingested_at)), 0))
           AS rows_per_second
FROM sensor_data;

SELECT * FROM ingest_rate;
```

Run the `SELECT` again every minute or so until `rows` reaches 4,380,050. On the test service, the load took about nine and a half minutes.

Example output:

```
  rows   | rows_per_batch | rows_per_second
---------+----------------+-----------------
 4380050 |            493 |            7738
(1 row)
```

The connector writes each batch in one transaction, and `now()` returns the time that transaction started, so every row in a batch has the same `ingested_at`. `rows_per_batch` divides the row count by the number of distinct `ingested_at` values.

</NumberedItem>
<NumberedItem title="Confirm each event became one row">

Count the rows and the chunks, and show the range of `time` and `ingested_at`, by running this SQL:

```sql
SELECT count(*) AS rows,
       min(time) AS first_reading,
       max(time) AS last_reading,
       min(ingested_at) AS first_ingested,
       max(ingested_at) AS last_ingested,
       (SELECT count(*) FROM show_chunks('sensor_data')) AS chunks
FROM sensor_data;
```

Verify the output shows 4,380,050 rows, readings that span ten years, and `ingested_at` values that span only the minutes of the load.

```
  rows   |     first_reading      |      last_reading      |        first_ingested         |         last_ingested         | chunks
---------+------------------------+------------------------+-------------------------------+-------------------------------+--------
 4380050 | 2016-08-29 18:00:00+00 | 2026-08-27 18:00:00+00 | 2026-11-26 21:13:35.325089+00 | 2026-11-26 21:23:01.363136+00 |    523
(1 row)
```

`time` holds the timestamp from each event, so every reading lands in the chunk for the week the sensor recorded it, and the table has about one chunk for each week of the ten years. A replayed event also carries the same `device_id`, `tag`, and `time` as it did the first time, so the upsert matches it to the row it already wrote.

</NumberedItem>

## Tune the batch size

<NumberedList>
<NumberedItem title="Delete the connector and empty the table">

Delete the connector by running this command:

```bash
curl -s -X DELETE http://localhost:8083/connectors/sensor-data-sink
```

Empty `sensor_data` by running this SQL in your `psql` session:

```sql
TRUNCATE sensor_data;
```

</NumberedItem>
<NumberedItem title="Register the connector with a larger batch size">

In `sink.json`, change `batch.size` and `consumer.override.max.poll.records` to `2000`. Register the connector under a new name, `sensor-data-sink-2000`, by running this command:

```bash
curl -s -X PUT -H "Content-Type: application/json" \
    -d @sink.json \
    http://localhost:8083/connectors/sensor-data-sink-2000/config
```

A new name gives the connector a new consumer group, so it reads the topic from the first event. The connector fills a batch only from the events that one poll of the topic returns, and a poll returns at most [`max.poll.records`](https://kafka.apache.org/43/configuration/consumer-configs/) events, so the batch grows only when both settings rise together.

</NumberedItem>
<NumberedItem title="Measure the rate, then repeat at a third batch size">

Query `ingest_rate` every minute or so until `rows` reaches 4,380,050 by running this SQL in your `psql` session:

```sql
SELECT * FROM ingest_rate;
```

Example output at a batch size of 2,000:

```
  rows   | rows_per_batch | rows_per_second
---------+----------------+-----------------
 4380050 |           1944 |            8932
(1 row)
```

Repeat Steps 1 to 3 with a batch size of 10,000. Delete `sensor-data-sink-2000`, empty the table, set both values in `sink.json` to `10000`, and register the connector as `sensor-data-sink-10000`.

Example output at a batch size of 10,000:

```
  rows   | rows_per_batch | rows_per_second
---------+----------------+-----------------
 4380050 |           8066 |            9430
(1 row)
```

Verify `rows_per_batch` and `rows_per_second` both rise with the batch size.

## Recover from a connector failure

<NumberedList>
<NumberedItem title="Empty the table and register the connector under a new name">

Delete the last connector by running this command:

```bash
curl -s -X DELETE http://localhost:8083/connectors/sensor-data-sink-10000
```

Run `TRUNCATE sensor_data;` in your `psql` session. Then register the connector as `sensor-data-sink-restart` by running this command:

```bash
curl -s -X PUT -H "Content-Type: application/json" \
    -d @sink.json \
    http://localhost:8083/connectors/sensor-data-sink-restart/config
```

</NumberedItem>
<NumberedItem title="Stop the Kafka Connect container while the connector writes">

Let the connector write for about 90 seconds. Then stop the container with no clean shutdown by running this command:

```bash
docker compose kill connect
```

</NumberedItem>
<NumberedItem title="Compare the committed offsets with the rows written">

Show the offsets the connector committed before it stopped by running this command:

```bash
docker compose exec kafka bin/kafka-consumer-groups.sh \
    --bootstrap-server localhost:9092 \
    --describe --group connect-sensor-data-sink-restart
```

Example output, trimmed to its first six columns:

```
GROUP                            TOPIC           PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
connect-sensor-data-sink-restart sensor_data     0          189124          876010          686886
connect-sensor-data-sink-restart sensor_data     1          189126          2628030         2438904
connect-sensor-data-sink-restart sensor_data     2          176078          876010          699932
```

Count the rows in the table by running this SQL in your `psql` session:

```sql
SELECT count(*) AS rows FROM sensor_data;
```

Verify the `CURRENT-OFFSET` values add up to less than `rows`.

```
  rows
--------
 829535
(1 row)
```

Kafka Connect commits the connector's offsets every 60 seconds by default. The connector wrote the rows above that total after its last commit, so it reads those events again when it restarts. In this example, the offsets add up to 554,328 and the table holds 829,535 rows, so the connector reads 275,207 events again.

</NumberedItem>
<NumberedItem title="Start the container again">

Start the Kafka Connect container by running this command:

```bash
docker compose start connect
```

Kafka Connect restarts the connector from its stored configuration, so you don't register it again. Query `ingest_rate` until `rows` reaches 4,380,050. It can take a minute before the count starts to rise.

</NumberedItem>
<NumberedItem title="Confirm the table has no duplicate rows">

Count the rows and the distinct readings by running this SQL:

```sql
SELECT count(*) AS rows,
       count(DISTINCT (device_id, tag, time)) AS distinct_readings
FROM sensor_data;
```

Verify `rows` and `distinct_readings` both equal 4,380,050, the number of events in the topic.

```
  rows   | distinct_readings
---------+-------------------
 4380050 |           4380050
(1 row)
```

The connector wrote the replayed events a second time, and each upsert updated the row that was already there.

## Troubleshooting

These problems can come up while you follow the tutorial. When a task fails, its status output shows `FAILED` and a `trace` field that holds the error. Check it with the status command in [Create the sink connector](#create-the-sink-connector).

- **The task fails with `Could not find table`.** The connector doesn't create tables unless you set `schema.evolution`, and `sensor_data` doesn't exist in the database that `connection.url` names. Create the hypertable and its unique index with the SQL in [Set up the data](#set-up-the-data). Then restart the task with `curl -s -X POST http://localhost:8083/connectors/sensor-data-sink/tasks/0/restart`.
- **The task fails with `there is no unique or exclusion constraint matching the ON CONFLICT specification`.** `sensor_data` has no unique index on exactly `device_id`, `tag`, and `time`, the columns in `primary.key.fields`. Create the index from [Set up the data](#set-up-the-data), then restart the task.
- **The task fails with `duplicate key value violates unique constraint` after a restart.** `insert.mode` is `insert`, the connector's default. The connector writes each replayed event as a plain `INSERT`, and the row it wrote before the restart blocks it. Set `insert.mode` to `upsert` in `sink.json`, send the file to the same connector name with the `PUT` command, and restart the task.
- **The task fails with `JsonConverter with schemas.enable requires "schema" and "payload" fields`.** An event on the topic is plain JSON with no schema, and the connector needs the schema to map each field to a column type. Publish events in the format `produce.py` uses. To replace events that are already on the topic, delete the connector, delete the topic with the `--delete` option of `kafka-topics.sh`, create the topic again, run `produce.py`, and register the connector under a new name.
- **`rows_per_second` stops rising at larger batch sizes.** Check `rows_per_batch` in `ingest_rate`. If it's far lower than `batch.size`, a consumer setting caps the batch. Set `consumer.override.max.poll.records` to the same value as `batch.size`. If `rows_per_batch` is still lower, raise `consumer.override.max.partition.fetch.bytes` above its default of 1 MiB, which limits how much data one fetch returns from each partition. If `rows_per_batch` matches `batch.size`, the batch size no longer limits the rate.

## Recap

In this tutorial, you streamed 4.4 million sensor readings from a Kafka topic into a hypertable, raised the connector's batch size, and restarted the connector partway through a load with no duplicate rows. Use this table as a reference for each part of the pipeline.

| Section | Technique | Why it matters |
|---|---|---|
| Set up the data | A unique index on `device_id`, `tag`, and `time` | The upsert needs a unique index on its key, and a hypertable's unique index has to include `time` |
| Publish the readings | Events that carry a schema and the reading's own timestamp | The connector maps each field to a column type, and each reading lands in the chunk for the week it was recorded |
| Create the sink connector | `insert.mode` set to `upsert`, with the key taken from the event's value | A replayed event updates the row it already wrote |
| Tune the batch size | `batch.size` and `consumer.override.max.poll.records` raised together | Each batch is one transaction, and a poll caps the size of a batch |
| Recover from a connector failure | A restart from the last committed offset | The connector reads some events twice, and the upserts keep one row for each |

These measurements were collected from a test Tiger Cloud service with 8 CPUs and 32 GiB of memory, running PostgreSQL 18.7 and TimescaleDB 2.32.1. Kafka 4.3.1 and Kafka Connect with Debezium 3.7.1 ran in Docker Desktop on a Windows computer, with 16 CPUs and about 15 GiB of memory available to Docker.

| Batch size | Rows per batch | Rows per second | Load time |
|---|---|---|---|
| 500, the default | 493 | 7,738 | 9 min 26 s |
| 2,000 | 1,944 | 8,932 | 8 min 10 s |
| 10,000 | 8,066 | 9,430 | 7 min 44 s |

At the default batch size, the connector commits a transaction for every 500 rows, and it loaded the topic at about 7,700 rows per second. At 10,000 rows per batch, the rate rose to about 9,400 rows per second, which cut the load from 9 minutes 26 seconds to 7 minutes 44 seconds. Most of that gain came from the first increase, from 500 to 2,000 rows. A connector that has to catch up after an outage or backfill a topic finishes about 18% sooner at the largest batch size. In the restart test, the connector read 275,207 events a second time, and the table still held 4,380,050 rows.

The same configuration works for any topic whose events carry a schema and a key that includes the event's timestamp.

For your next step, stop and restart a sink connector on one of your own topics while it writes. Then compare `count(*)` with the distinct count of the columns that identify an event. If the two counts differ, the connector wrote replayed events as new rows, and the table needs a unique index on those columns with `insert.mode` set to `upsert`.
