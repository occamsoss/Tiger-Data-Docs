This tutorial shows you how to design a schema for Tiger Data in stages, and how to measure each stage with the same five queries. You will create three versions of one table, where version 1 is a plain PostgreSQL table, version 2 has column types that fit the data, and version 3 is a hypertable that will then get keys and the columnstore. The data is three months of [311 service requests](https://data.cityofnewyork.us/Social-Services/311-Service-Requests-from-2020-to-Present/erm2-nwe9/about_data) from NYC Open Data, which is about 1 million requests that New York City residents sent to city agencies.

If you want an overview of the decisions in a data model first, see [Design your data model](https://www.tigerdata.com/docs/learn/data-model/design-your-data-model).

## What you learn

- How to choose column types, a partition column, and a chunk interval.
- Why a primary key on a hypertable includes the partition column.
- How to choose `segmentby` and `orderby` for the columnstore.
- Which query patterns a schema serves well and poorly, shown in `EXPLAIN` output.

Install `psycopg`, the PostgreSQL driver for Python, by running this command:

```bash
pip install "psycopg[binary]"
```

Save this script as `load_requests.py` and run it in the same directory.

```python
"""
Load service_requests.csv into the requests_v1 table.

The script shifts every timestamp forward so the newest request
falls in the current hour, and stores empty fields as NULL.
"""
import csv
import os
import sys
from datetime import datetime, timezone
from pathlib import Path

import psycopg

CSV_PATH = Path(__file__).resolve().parent / "service_requests.csv"
COLUMNS = [
    "unique_key", "created_date", "closed_date", "agency", "agency_name",
    "complaint_type", "descriptor", "status", "borough", "incident_zip",
    "council_district", "latitude", "longitude",
]
COPY_SQL = f"COPY requests_v1 ({', '.join(COLUMNS)}) FROM STDIN"


def read_rows():
    with CSV_PATH.open(newline="", encoding="utf-8") as f:
        yield from csv.DictReader(f)


def main():
    url = os.environ.get("DATABASE_URL")
    if not url:
        sys.exit("Set DATABASE_URL to your service connection string.")
    if not CSV_PATH.exists():
        sys.exit(f"Can't find {CSV_PATH}. Download the dataset first.")

    print("Finding the newest request in the file...")
    newest = max(
        datetime.fromisoformat(r["created_date"]) for r in read_rows()
    )
    this_hour = datetime.now(timezone.utc).replace(
        minute=0, second=0, microsecond=0, tzinfo=None
    )
    shift = this_hour - newest
    print(f"Shifting timestamps forward by {shift.days} days.")

    with psycopg.connect(url) as conn:
        with conn.cursor() as cur:
            cur.execute("SELECT count(*) FROM requests_v1")
            if cur.fetchone()[0] > 0:
                sys.exit("requests_v1 already has rows. Nothing loaded.")

            with cur.copy(COPY_SQL) as copy:
                for count, r in enumerate(read_rows(), start=1):
                    row = [r[column] or None for column in COLUMNS]
                    for i in (1, 2):
                        if row[i]:
                            row[i] = datetime.fromisoformat(row[i]) + shift
                    copy.write_row(row)
                    if count % 100_000 == 0:
                        print(f"Sent {count:,} rows...")

    print(f"Loaded {count:,} rows into requests_v1.")


if __name__ == "__main__":
    main()
```

The script shifts every timestamp forward by the same amount so the newest request falls in the current hour in UTC. The shift makes queries about today and the past 30 days return data. Those queries count back from the current time, so complete the tutorial on the day you load the data.

Verify the script loaded about 1 million rows into the table.

```
Finding the newest request in the file...
Shifting timestamps forward by 26 days.
Sent 100,000 rows...
...
Loaded 1,000,226 rows into requests_v1.
```

## Measure the naive schema

<NumberedList>
<NumberedItem title="Create the benchmark function">

Create a function that runs five queries against a table with [`EXPLAIN (ANALYZE, BUFFERS)`](https://www.postgresql.org/docs/current/sql-explain.html), and returns the execution time and the buffer count of each one, by running this SQL:

```sql
CREATE OR REPLACE FUNCTION benchmark(tbl regclass)
RETURNS TABLE (query text, execution_ms numeric, buffers bigint)
LANGUAGE plpgsql AS $$
DECLARE
    today   timestamptz := date_trunc('day', now());
    key     bigint;
    plan    json;
    names   text[] := ARRAY['1. Newest requests', '2. One day',
                            '3. 30-day aggregate', '4. One request',
                            '5. One agency'];
    queries text[] := ARRAY[
        'SELECT unique_key, created_date, agency, complaint_type
         FROM %1$s
         ORDER BY created_date DESC
         LIMIT 10',

        'SELECT complaint_type, count(*) AS requests
         FROM %1$s
         WHERE created_date >= %2$L AND created_date < %3$L
         GROUP BY complaint_type
         ORDER BY requests DESC
         LIMIT 5',

        'SELECT agency, count(*) AS requests, count(closed_date) AS closed
         FROM %1$s
         WHERE created_date >= %4$L
         GROUP BY agency
         ORDER BY requests DESC',

        'SELECT unique_key, created_date, agency, complaint_type, status
         FROM %1$s
         WHERE unique_key = %5$s',

        'SELECT complaint_type, count(*) AS requests
         FROM %1$s
         WHERE agency = ''DOT'' AND created_date >= %4$L
         GROUP BY complaint_type
         ORDER BY requests DESC
         LIMIT 5'
    ];
BEGIN
    EXECUTE format('SELECT unique_key FROM %s ORDER BY created_date LIMIT 1', tbl)
    INTO key;

    FOR i IN 1 .. 5 LOOP
        EXECUTE 'EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) '
             || format(queries[i], tbl, today - INTERVAL '1 day', today,
                       today - INTERVAL '30 days', key)
        INTO plan;
        query := names[i];
        execution_ms := round((plan->0->>'Execution Time')::numeric, 2);
        buffers := (plan->0->'Plan'->>'Shared Hit Blocks')::bigint
                 + (plan->0->'Plan'->>'Shared Read Blocks')::bigint;
        RETURN NEXT;
    END LOOP;
END
$$;
```

A buffer is an 8 kB block of table or index data, so the buffer count shows how much data a query read.

## Choose column types

<NumberedList>
<NumberedItem title="Create the version 2 tables">

Create a lookup table for the agencies and the second version of the requests table by running this SQL:

```sql
CREATE TABLE agencies (
    agency      text PRIMARY KEY,
    agency_name text NOT NULL
);

CREATE TABLE requests_v2 (
    unique_key       integer NOT NULL,
    created_date     timestamptz NOT NULL,
    closed_date      timestamptz,
    agency           text NOT NULL,
    complaint_type   text NOT NULL,
    descriptor       text,
    status           text NOT NULL,
    borough          text NOT NULL,
    incident_zip     text,
    council_district smallint,
    latitude         double precision,
    longitude        double precision
);
```

Version 2 makes four changes to the columns.

- `timestamptz` stores each time as a point in time, so a value means the same moment in every session time zone.
- `integer`, `smallint`, and `double precision` are the smallest numeric types that fit these values, and each one takes less space than `numeric`.
- `NOT NULL` makes PostgreSQL reject a request that arrives without a required value.
- The `agencies` lookup table stores each agency's name once, so the names no longer repeat in every request.

</NumberedItem>
<NumberedItem title="Copy the rows into version 2">

Copy the agencies and the requests into the new tables by running this SQL:

## Choose a partition column and chunk interval

The partition column for version 3 is `created_date`. Four of the five benchmark queries filter or sort on it, every request has a value for it, and the value never changes.

<NumberedList>
<NumberedItem title="Create the version 3 hypertable">

Create the third version as a [hypertable](https://www.tigerdata.com/docs/learn/hypertables/understand-hypertables) with [`CREATE TABLE ... WITH`](https://www.tigerdata.com/docs/reference/timescaledb/hypertables/create_table) by running this SQL:

```sql
CREATE TABLE requests_v3 (
    LIKE requests_v2
) WITH (
    tsdb.hypertable,
    tsdb.partition_column = 'created_date',
    tsdb.chunk_interval = '7 days',
    tsdb.columnstore = false
);
```

</NumberedItem>
<NumberedItem title="Copy the rows and run the benchmark">

Copy the rows into `requests_v3` and run the benchmark with these statements:

```sql
INSERT INTO requests_v3
SELECT * FROM requests_v2;

ANALYZE requests_v3;

SELECT * FROM benchmark('requests_v3');

SELECT pg_size_pretty(hypertable_size('requests_v3')) AS table_size;
```

Verify Queries 1 and 2 read far fewer buffers than on version 2.

```
        query        | execution_ms | buffers
---------------------+--------------+---------
 1. Newest requests  |         0.16 |      42
 2. One day          |         3.60 |     218
 3. 30-day aggregate |        34.10 |    5704
 4. One request      |        25.07 |   16473
 5. One agency       |        18.17 |    5704
(5 rows)

 table_size
------------
 165 MB
(1 row)
```

TimescaleDB stores the requests in 7-day chunks, and reads only the chunks that a query's time filter covers. Query 2 asks for one day, so it reads one chunk. The table is larger than version 2 because a hypertable has an index on its partition column by default.

</NumberedItem>
<NumberedItem title="Check the chunk interval">

Compare the largest index of a single chunk with `shared_buffers` by running this SQL:

```sql
SELECT pg_size_pretty(max(index_bytes)) AS largest_chunk_index,
       current_setting('shared_buffers') AS shared_buffers
FROM chunks_detailed_size('requests_v3');
```

Verify the index is a small fraction of `shared_buffers`.

```
 largest_chunk_index | shared_buffers
---------------------+----------------
 3040 kB             | 8GB
(1 row)
```

The [chunk sizing guide](https://www.tigerdata.com/docs/learn/hypertables/sizing-hypertable-chunks) says the indexes of the chunks that receive new data should fit in about 25% of main memory, which is the `shared_buffers` setting. This data leaves room for a much longer interval. The default of 7 days keeps a one-day or one-week query on one or two chunks, and a longer interval would make those queries read more rows than they need.

## Choose segmentby and orderby

The [columnstore](https://www.tigerdata.com/docs/learn/columnar-storage/understand-hypercore) groups the rows of each chunk by the `segmentby` column, sorts each group by `orderby`, and compresses each group in batches of up to 1,000 rows.

<NumberedList>
<NumberedItem title="Count the rows for each candidate column">

Count the rows in a 7-day range, which is what one chunk holds, and the average number of rows for each value of four candidate `segmentby` columns, by running this SQL:

```sql
SELECT count(*) AS rows,
       count(*) / count(DISTINCT agency) AS per_agency,
       count(*) / count(DISTINCT borough) AS per_borough,
       count(*) / count(DISTINCT complaint_type) AS per_complaint_type,
       count(*) / count(DISTINCT unique_key) AS per_unique_key
FROM requests_v3
WHERE created_date >= now() - INTERVAL '14 days'
  AND created_date < now() - INTERVAL '7 days';
```

Example output:

```
 rows  | per_agency | per_borough | per_complaint_type | per_unique_key
-------+------------+-------------+--------------------+----------------
 83210 |       5943 |       13868 |                526 |              1
(1 row)
```

A `segmentby` column is one that queries filter or group on, with enough rows for each value in a chunk to fill batches. Queries 3 and 5 use `agency`, which averages thousands of rows for each value, so it is the `segmentby` column. `unique_key` has one row for each value, which would put every row in a batch of its own.

</NumberedItem>
<NumberedItem title="Turn on the columnstore">

Turn on the columnstore for `requests_v3` by running this SQL:

```sql
ALTER TABLE requests_v3 SET (
    tsdb.enable_columnstore = true,
    tsdb.segmentby = 'agency',
    tsdb.orderby = 'created_date DESC, unique_key'
);
```

Sorting by `created_date DESC` matches the order that queries read requests in. `unique_key` follows it because the columnstore checks the primary key faster when every key column is in `segmentby` or `orderby`.

</NumberedItem>
<NumberedItem title="Convert the chunks">

Convert every chunk to the columnstore with [`convert_to_columnstore()`](https://www.tigerdata.com/docs/reference/timescaledb/hypercore/convert_to_columnstore) by running this SQL:

```sql
DO $$
DECLARE
    chunk regclass;
BEGIN
    FOR chunk IN SELECT c FROM show_chunks('requests_v3') AS c LOOP
        CALL convert_to_columnstore(chunk);
    END LOOP;
END
$$;
```

In an application, a [columnstore policy](https://www.tigerdata.com/docs/reference/timescaledb/hypercore/add_columnstore_policy) converts chunks as they age.

</NumberedItem>
<NumberedItem title="Compare storage and run the benchmark">

Show the size of `requests_v3` before and after compression with [`hypertable_columnstore_stats()`](https://www.tigerdata.com/docs/reference/timescaledb/hypercore/hypertable_columnstore_stats), and run the benchmark, with these statements:

## Fix queries the schema serves poorly

The columnstore serves a query well when the planner knows the query's time range before the query runs, or when the query reads rows in the columnstore's order. Each query in this section does neither, and each rewrite changes that.

### A lookup with no time filter

Save the key and creation time of the oldest request as `psql` variables, and run `EXPLAIN (ANALYZE, BUFFERS)` on a lookup by key alone, by running this SQL:

```sql
FROM requests_v3
ORDER BY created_date
LIMIT 1
\gset

SELECT unique_key, created_date, agency, complaint_type, status
FROM requests_v3
WHERE unique_key = :lookup_key;
```

```sql
WHERE created_date >= clock_timestamp() - INTERVAL '1 day'
```

```sql
    period text PRIMARY KEY,
    starts timestamptz NOT NULL,
    ends   timestamptz NOT NULL

INSERT INTO report_periods
```

## Troubleshooting

These problems can come up while you follow the tutorial:

- **The loading script stops with a `KeyError`, a `ValueError`, or a `TypeError`, or it loads far fewer than 1 million rows.** The download stopped early or returned an error message, so `service_requests.csv` is incomplete. Run the `curl` command in [Set up the data](#set-up-the-data) again, run `TRUNCATE requests_v1;`, then run the script again.
- **The loading script says `requests_v1` already has rows.** An earlier run of the script loaded the table. To load the data again, run `TRUNCATE requests_v1;`, then run the script again.
- **A query fails with a syntax error at or near `:`.** A `psql` variable is missing, usually after a reconnect. Run the SQL block that contains `\gset` again, in [A lookup with no time filter](#a-lookup-with-no-time-filter) or [Time bounds from a join](#time-bounds-from-a-join).

## Recap

In this tutorial, you designed a schema in stages and measured each stage with the same five queries. Use this table to pair each decision with the result it changed.

| Decision | In this tutorial | Result it changed |
|---|---|---|
| Column types | `timestamptz`, the smallest numeric types that fit, `NOT NULL`, and a lookup table | A smaller table |
| Partition column and chunk interval | `created_date` and 7 days | A query with a time filter reads only the chunks in its range |
| Keys | A primary key on `unique_key` and `created_date`, and a foreign key to `agencies` | The single-row lookup uses an index |
| `segmentby` and `orderby` | `agency`, then `created_date DESC` and `unique_key` | A smaller table and a faster 30-day aggregate |
| Query shape | A time filter the planner knows before the query runs, and `DISTINCT ON` the `segmentby` column | Fewer chunks and buffers read |

These measurements were collected from a test Tiger Cloud service with 8 CPUs and 32 GiB of memory, running PostgreSQL 18.7 and TimescaleDB 2.32.1. Times are the `execution_ms` values that `benchmark()` returned at each stage.

| Measurement | Version 1 | Version 2 | Version 3 | Version 3 with keys | Version 3 in the columnstore |
|---|---|---|---|---|---|
| Table size | 176 MB | 129 MB | 165 MB | 196 MB | 31 MB |
| Query 1, newest requests | 94 ms | 94 ms | 0.16 ms | 0.17 ms | 3.4 ms |
| Query 2, one day | 33 ms | 36 ms | 3.6 ms | 3.5 ms | 0.56 ms |
| Query 3, 30-day aggregate | 52 ms | 54 ms | 34 ms | 34 ms | 12 ms |
| Query 4, one request | 39 ms | 35 ms | 25 ms | 0.37 ms | 0.70 ms |
| Query 5, one agency | 35 ms | 39 ms | 18 ms | 18 ms | 0.88 ms |

Column types made the table about 27% smaller, but every query still read the whole table. Partitioning made the one-day query 10 times faster, because the query reads one chunk out of 14, and that difference grows as the table grows. The columnstore reduced the table to about one sixth of its size and made the 30-day aggregate about 3 times faster. Queries 1 and 4 return a few rows, so they ran faster through the rowstore's indexes.

For your next step, take one of your own tables through the same stages, and replace the five queries in `benchmark()` with your five most frequent queries. The numbers from the first stage give you a baseline, so you can see what each decision changes on your own data before you change a production table.
