This tutorial shows you how to design a schema for Tiger Data in three versions, and how to measure each version with the same five queries. It uses three months of [311 service requests](https://data.cityofnewyork.us/Social-Services/311-Service-Requests-from-2020-to-Present/erm2-nwe9/about_data) from NYC Open Data, which is about 1 million requests that New York City residents sent to city agencies.

If you want an overview of the decisions in a data model first, see [Design your data model](https://www.tigerdata.com/docs/learn/data-model/design-your-data-model).

## What you learn

- How to choose column types, a partition column, and a chunk interval.
- Why a primary key on a hypertable includes the partition column.
- How to choose `segmentby` and `orderby` for the columnstore.
- Which table layout fits a workload.
- Which query patterns a schema serves well and poorly, shown in `EXPLAIN` output.

```python
"""
Load service_requests.csv into the requests_v1 table.

The script shifts every timestamp forward so the newest request
falls in the current hour, and stores empty fields as NULL.
"""
import csv
import os
import sys
from datetime import datetime, timezone
from pathlib import Path

import psycopg

CSV_PATH = Path(__file__).resolve().parent / "service_requests.csv"
COLUMNS = [
    "unique_key", "created_date", "closed_date", "agency", "agency_name",
    "complaint_type", "descriptor", "status", "borough", "incident_zip",
    "council_district", "latitude", "longitude",
]
COPY_SQL = f"COPY requests_v1 ({', '.join(COLUMNS)}) FROM STDIN"


def read_rows():
    with CSV_PATH.open(newline="", encoding="utf-8") as f:
        yield from csv.DictReader(f)


def main():
    url = os.environ.get("DATABASE_URL")
    if not url:
        sys.exit("Set DATABASE_URL to your service connection string.")
    if not CSV_PATH.exists():
        sys.exit(f"Can't find {CSV_PATH}. Download the dataset first.")

    print("Finding the newest request in the file...")
    newest = max(
        datetime.fromisoformat(r["created_date"]) for r in read_rows()
    )
    this_hour = datetime.now(timezone.utc).replace(
        minute=0, second=0, microsecond=0, tzinfo=None
    )
    shift = this_hour - newest
    print(f"Shifting timestamps forward by {shift.days} days.")

    with psycopg.connect(url) as conn:
        with conn.cursor() as cur:
            cur.execute("SELECT count(*) FROM requests_v1")
            if cur.fetchone()[0] > 0:
                sys.exit("requests_v1 already has rows. Nothing loaded.")

            with cur.copy(COPY_SQL) as copy:
                for count, r in enumerate(read_rows(), start=1):
                    row = [r[column] or None for column in COLUMNS]
                    for i in (1, 2):
                        if row[i]:
                            row[i] = datetime.fromisoformat(row[i]) + shift
                    copy.write_row(row)
                    if count % 100_000 == 0:
                        print(f"Sent {count:,} rows...")

    print(f"Loaded {count:,} rows into requests_v1.")


if __name__ == "__main__":
    main()
```

The script shifts every timestamp forward by the same amount so the newest request falls in the current hour in UTC. The shift makes queries about today and the past 30 days return data.

```
...
Loaded 1,000,226 rows into requests_v1.
```

## Choose column types

<NumberedList>
<NumberedItem title="Create the version 2 tables">

Save this SQL as `schema_v2.sql` and run it with `\i schema_v2.sql`:

```sql
CREATE TABLE agencies (
    agency      text PRIMARY KEY,
    agency_name text NOT NULL
);

CREATE TABLE requests_v2 (
    unique_key       integer NOT NULL,
    created_date     timestamptz NOT NULL,
    closed_date      timestamptz,
    agency           text NOT NULL,
    complaint_type   text NOT NULL,
    descriptor       text,
    status           text NOT NULL,
    borough          text NOT NULL,
    incident_zip     text,
    council_district smallint,
    latitude         double precision,
    longitude        double precision
);
```

Version 2 makes four changes to the columns.

- `timestamptz` stores each time as a point in time, so a value means the same moment in every session time zone.
- `integer`, `smallint`, and `double precision` are the smallest numeric types that fit these values, and each one takes less space than `numeric`.
- `NOT NULL` makes PostgreSQL reject a request that arrives without a required value.
- The `agencies` lookup table stores each agency's name once, so the names no longer repeat in every request.

## Choose a partition column and chunk interval

The partition column for version 3 is `created_date`. Four of the five benchmark queries filter or sort on it, every request has a value for it, and the value never changes.

<NumberedList>
<NumberedItem title="Compare index growth with shared_buffers">

A [hypertable](https://www.tigerdata.com/docs/learn/hypertables/understand-hypertables) has an index on its partition column by default. Create that index on `requests_v2` and estimate how much it grows in 1 day, 7 days, and 30 days by running this SQL:

```sql
CREATE INDEX requests_v2_created_date_idx
    ON requests_v2 (created_date DESC);

SELECT i AS chunk_interval,
       pg_size_pretty((pg_indexes_size('requests_v2')
           * extract(epoch FROM i)
           / extract(epoch FROM s.last - s.first))::bigint)
           AS index_growth,
       current_setting('shared_buffers') AS shared_buffers
FROM unnest(ARRAY['1 day', '7 days', '30 days']::interval[]) AS i,
     (SELECT min(created_date) AS first, max(created_date) AS last
      FROM requests_v2) AS s;
```

Verify the index growth for every interval is a small fraction of `shared_buffers`.

```
 chunk_interval | index_growth | shared_buffers
----------------+--------------+----------------
 1 day          | 223 kB       | 8GB
 7 days         | 1563 kB      | 8GB
 30 days        | 6699 kB      | 8GB
(3 rows)
```

The [chunk sizing guide](https://www.tigerdata.com/docs/learn/hypertables/sizing-hypertable-chunks) says to choose an interval whose index growth fits in `shared_buffers`, which is about 25% of main memory. All three intervals fit, so the choice depends on the queries. A shorter interval makes more chunks, and each chunk adds planning work to a query that covers a long time range. This tutorial uses 7 days, the TimescaleDB default, so a one-day query reads one chunk and a 30-day query reads five or six.

</NumberedItem>
<NumberedItem title="Create the version 3 hypertable">

Save this SQL as `schema_v3.sql` and run it with `\i schema_v3.sql`. It uses [`CREATE TABLE ... WITH`](https://www.tigerdata.com/docs/reference/timescaledb/hypertables/create_table) to create a hypertable with the columns of `requests_v2`.

```sql
CREATE TABLE requests_v3 (
    LIKE requests_v2
) WITH (
    tsdb.hypertable,
    tsdb.partition_column = 'created_date',
    tsdb.chunk_interval = '7 days',
    tsdb.columnstore = false
);
```

## Choose segmentby and orderby

The [columnstore](https://www.tigerdata.com/docs/learn/columnar-storage/understand-hypercore) groups the rows of each chunk by the `segmentby` column, sorts each group by `orderby`, and compresses each group in batches of up to 1,000 rows.

<NumberedList>
<NumberedItem title="Count the rows for each candidate column">

```sql

FROM timescaledb_information.chunks
WHERE hypertable_name = 'requests_v3'
ORDER BY range_start DESC
LIMIT 1 OFFSET 1

       count(*) / count(DISTINCT borough) AS per_borough,
       count(*) / count(DISTINCT complaint_type) AS per_complaint_type,
       count(*) / count(DISTINCT unique_key) AS per_unique_key
FROM :sample_chunk;
```

Example output:

```

-------+------------+-------------+--------------------+----------------
 80625 |       5758 |       13437 |                500 |              1
(1 row)
```

A `segmentby` column needs two things. Queries filter or group on it, and each of its values has enough rows in a chunk to fill batches. Queries 3 and 5 use `agency`, and `agency` averages thousands of rows for each value in a chunk, so it is the `segmentby` column. A column such as `unique_key`, with one row for each value, would put every row in a batch of its own.

</NumberedItem>
<NumberedItem title="Turn on the columnstore">

Turn on the columnstore for `requests_v3` by running this SQL:

```sql
ALTER TABLE requests_v3 SET (
    tsdb.enable_columnstore = true,
    tsdb.segmentby = 'agency',
    tsdb.orderby = 'created_date DESC, unique_key'
);
```

Sorting by `created_date DESC` matches the order that queries read requests in. `unique_key` follows it because the columnstore checks the primary key faster when every key column is in `segmentby` or `orderby`.

## Choose a table layout

`requests_v3` is a wide table, with one row for each request and one typed column for each attribute. [Wide, narrow, and medium tables](https://www.tigerdata.com/docs/learn/data-model/wide-narrow-medium-tables) describes three layouts, and this table shows how each one would hold the 311 data.

| Layout | Shape for this dataset | Fits when |
|---|---|---|
| Wide | One row for each request, with a column for each attribute, as in `requests_v3` | You know the attributes up front, and queries read several of them together |
| Narrow | One table for each kind of event, such as `request_opened` and `request_closed`, each with a time, a key, and one or two values | You track a small, fixed set of values and query each one by itself |
| Medium | One row for each attribute of a request, with an `attribute` name column and one value column for each data type | Attributes change often, or differ from one agency to the next |

A wide table fits this dataset, because every request has the same attributes and the benchmark queries read several of them from each row.

Split data across more than one hypertable in these three cases.

- **Tenant.** Give a tenant its own hypertable when it needs its own columns or its own retention period. When tenants share both, keep them in one hypertable with a tenant column in `segmentby`, as `agency` is here.
- **Data type.** Give a second kind of data its own hypertable when its columns or its arrival rate differ. A log of status changes for each request would be a second hypertable, because the columns, the chunk interval, `segmentby`, and `orderby` all belong to one hypertable.
- **Retention period.** A [data retention policy](https://www.tigerdata.com/docs/reference/timescaledb/data-retention/add_retention_policy) drops whole chunks from one hypertable, so data that you keep for different lengths of time goes in different hypertables.

## Fix queries the schema serves poorly

Version 3 serves a query well in two cases. The query filters on `created_date` with a value the planner knows before the query runs, or it reads rows in the columnstore's order. Each of the four queries in this section does neither, and each rewrite changes that.

## Troubleshooting

These problems can come up while you follow the tutorial.

- **`ALTER TABLE` still fails with `cannot create a unique index without the column "created_date"`.** The primary key's column list leaves out `created_date`. Run the second statement in [Add keys and constraints](#add-keys-and-constraints), which lists `unique_key` and `created_date`. Any unique index you add later needs `created_date` in its column list as well.
- **`ALTER TABLE` warns that `unique_key` should be used for segmenting or ordering.** The `tsdb.orderby` setting leaves out `unique_key`, which is part of the primary key. Run the `ALTER TABLE` statement in [Choose segmentby and orderby](#choose-segmentby-and-orderby) again with `unique_key` in `tsdb.orderby`. The new setting applies to the chunks you convert after that.
- **A plan shows a columnstore scan before [Choose segmentby and orderby](#choose-segmentby-and-orderby).** A columnstore policy converted chunks in the background, which happens when `schema_v3.sql` leaves out `tsdb.columnstore = false`. Run `DROP TABLE requests_v3;`, add the option to the file, run the file, and copy the rows again.
- **A query fails with a syntax error at or near `:`.** The `psql` variables are missing, usually after a reconnect. Run the `\gset` block in [Set up the data](#set-up-the-data) again, and set `tbl` again with `\set tbl requests_v3`.
- **A plan shows a different scan type from the tutorial.** Run `ANALYZE` on the table and run the plan again. PostgreSQL versions and service sizes can choose different scan types, and the chunk lines and buffer counts show the same result in either case.

## Recap

In this tutorial, you designed a schema in three versions and measured each one with the same five queries. Use this table to pair each decision with the result it changed.

| Decision | Choice in this tutorial | Result it changed |
|---|---|---|
| Column types | `timestamptz`, the smallest numeric types that fit, `NOT NULL`, and a lookup table | A smaller table |
| Partition column and chunk interval | `created_date` and 7 days | A query with a time filter reads only the chunks in its range |
| Keys | A primary key on `unique_key` and `created_date`, and a foreign key to `agencies` | The single-row lookup uses an index |
| `segmentby` and `orderby` | `agency`, then `created_date DESC` and `unique_key` | A smaller table and a faster 30-day aggregate |
| Query shape | A time filter the planner knows before the query runs, and `DISTINCT ON` the `segmentby` column | Fewer chunks and buffers read |

These measurements were collected from a test Tiger Cloud service with 8 CPUs and 32 GiB of memory, running PostgreSQL 18.7 and TimescaleDB 2.32.1. Times are the `Execution Time` of each query, from the second run of each benchmark.

| Measurement | Version 1 | Version 2 | Version 3 | Version 3 with keys | Version 3 in the columnstore |
|---|---|---|---|---|---|
| Table size | 176 MB | 129 MB | 165 MB | 196 MB | 31 MB |
| Query 1, newest requests | 96 ms | 90 ms | 0.16 ms | 0.18 ms | 0.31 ms |
| Query 2, one day | 35 ms | 31 ms | 4.5 ms | 4.5 ms | 0.70 ms |
| Query 3, 30-day aggregate | 52 ms | 50 ms | 36 ms | 37 ms | 12 ms |
| Query 4, one request | 41 ms | 30 ms | 28 ms | 0.13 ms | 0.53 ms |
| Query 5, one agency | 37 ms | 35 ms | 25 ms | 21 ms | 0.91 ms |

Column types made the table about 27% smaller, from 176 MB to 129 MB, and every query still read every row. Partitioning shortened the one-day query from 31 ms to 4.5 ms, because the query reads one chunk out of 15. The difference grows with the table. A query on a regular table scans more rows every month, and a one-day query on the hypertable keeps reading one chunk. The hypertable's indexes brought the table to 196 MB, and the columnstore then reduced it to 31 MB and shortened the 30-day aggregate from 37 ms to 12 ms.

For your next step, write the three versions for one of your own tables and run your five most frequent queries against each one. The version 1 numbers give you a baseline, so you can see what each decision changes on your own data before you change a production table.
