This tutorial shows you how to fix a slow production Tiger Cloud service from an AI agent with Tiger CLI and Tiger MCP. It uses a sample manufacturing dataset that has hourly readings from ten sensors on each of five factory machines, over ten years, with about 4.4 million records in total. The agent is Claude Code.

If you want an overview of Tiger CLI and Tiger MCP first, see [Tiger CLI and Tiger MCP](https://www.tigerdata.com/docs/learn/tiger-cli-mcp).

## What you learn

- How to restrict an agent to read-only access on a production service.
- How to find a slow query from an agent with service metrics, logs, and `pg_stat_statements`.
- How to test a `segmentby` change on a fork with the agent.
- How to apply a reviewed change to production with Tiger CLI and verify it.

## Set up the data

<NumberedList>
<NumberedItem title="Create a Tiger Cloud service">

Create a Tiger Cloud service by following [our previous guide](https://www.tigerdata.com/docs/get-started/quickstart/create-service). Download the configuration file when you create it, and keep it for the next step. The file holds your connection string.

</NumberedItem>
<NumberedItem title="Connect to your service">

Save your connection string in the `DATABASE_URL` environment variable and connect to your database with these commands:

```bash
export DATABASE_URL="<connection string>"
psql "$DATABASE_URL"
```

Initializing `DATABASE_URL` is required for the loading script in Step 4.

</NumberedItem>
<NumberedItem title="Create the hypertable">

Create the `sensor_data` hypertable by running this SQL in your `psql` session:

```sql
CREATE TABLE sensor_data (
    reading_id  bigint NOT NULL,
    time        timestamptz NOT NULL,
    device_id   text NOT NULL,
    tag         text NOT NULL,
    value       double precision,
    unit        text,
    description text
) WITH (
    tsdb.hypertable,
    tsdb.partition_column = 'time',
    tsdb.chunk_interval = '7 days',
    tsdb.segmentby = ''
);
```

This statement turns the [columnstore](https://www.tigerdata.com/docs/learn/columnar-storage/understand-hypercore) on by default. The empty `tsdb.segmentby` leaves the columnstore with no `segmentby` column, which is the problem you will fix later in this tutorial.

</NumberedItem>
<NumberedItem title="Load the manufacturing dataset">

Type `\q` to quit `psql`. Stay in the same terminal, so `DATABASE_URL` keeps its value, and download `manufacturing.zip`.

Unzip the dataset and install `psycopg`, the PostgreSQL driver for Python, by running these commands:

```bash
unzip manufacturing.zip
pip install "psycopg[binary]"
```

Save this script as `load_data.py` and run it in the same directory. It may take a minute or two, depending on your internet connection.

```python
"""
Load manufacturing.csv into the sensor_data hypertable.

The script numbers each reading in file order, which is time order,
and shifts every timestamp forward so the newest reading falls in
the current hour.
"""
import csv
import os
import sys
from datetime import datetime, timezone
from pathlib import Path

import psycopg

CSV_PATH = Path(__file__).resolve().parent / "manufacturing.csv"
COPY_SQL = """
    COPY sensor_data
        (reading_id, time, device_id, tag, value, unit, description)
    FROM STDIN
"""


def read_rows():
    with CSV_PATH.open(newline="", encoding="utf-8") as f:
        yield from csv.DictReader(f)


def main():
    url = os.environ.get("DATABASE_URL")
    if not url:
        sys.exit("Set DATABASE_URL to your service connection string.")
    if not CSV_PATH.exists():
        sys.exit(f"Can't find {CSV_PATH}. Unzip manufacturing.zip first.")

    print("Finding the newest reading in the file...")
    newest = max(datetime.fromisoformat(r["time"]) for r in read_rows())
    this_hour = datetime.now(timezone.utc).replace(
        minute=0, second=0, microsecond=0
    )
    shift = this_hour - newest
    print(f"Shifting timestamps forward by {shift.days} days.")

    with psycopg.connect(url) as conn:
        with conn.cursor() as cur:
            cur.execute("SELECT count(*) FROM sensor_data")
            if cur.fetchone()[0] > 0:
                sys.exit("sensor_data already has rows. Nothing loaded.")

            with cur.copy(COPY_SQL) as copy:
                for reading_id, r in enumerate(read_rows(), start=1):
                    copy.write_row((
                        reading_id,
                        datetime.fromisoformat(r["time"]) + shift,
                        r["device_id"],
                        r["tag"],
                        r["value"],
                        r["unit"],
                        r["description"],
                    ))
                    if reading_id % 500_000 == 0:
                        print(f"Sent {reading_id:,} rows...")

    print(f"Loaded {reading_id:,} rows into sensor_data.")


if __name__ == "__main__":
    main()
```

The loading script does three things:

- It reads the file once to find the newest reading, then shifts every timestamp forward by the same amount so the newest reading falls in the current hour.
- It numbers the readings in the order they appear in the file, which is time order, and stores the number in `reading_id`.
- It streams the rows into `sensor_data` with the PostgreSQL `COPY` command, which is much faster than inserting rows one at a time.

Verify the script loaded about 4.4 million rows into the table.

```
Finding the newest reading in the file...
Shifting timestamps forward by 91 days.
Sent 500,000 rows...
Sent 1,000,000 rows...
Sent 1,500,000 rows...
Sent 2,000,000 rows...
Sent 2,500,000 rows...
Sent 3,000,000 rows...
Sent 3,500,000 rows...
Sent 4,000,000 rows...
Loaded 4,380,050 rows into sensor_data.
```

<NumberedItem title="Convert every chunk to the columnstore">

Convert every chunk to the columnstore with [`convert_to_columnstore()`](https://www.tigerdata.com/docs/reference/timescaledb/hypercore/convert_to_columnstore) and count the converted chunks by running this SQL:

```sql
DO $$
DECLARE
    chunk regclass;
BEGIN
    FOR chunk IN SELECT c FROM show_chunks('sensor_data') AS c LOOP
        CALL convert_to_columnstore(chunk);
    END LOOP;
END
$$;

SELECT is_compressed, count(*) AS chunks
FROM timescaledb_information.chunks
WHERE hypertable_name = 'sensor_data'
GROUP BY is_compressed;
```

Verify the output shows every chunk with `is_compressed` set to `t`.

```
DO
 is_compressed | chunks 
---------------+--------
 t             |    523
(1 row)
```

```bash
tiger auth login

```

Replace `<service-id>` with your service ID and save the database password for your service with this command:

```bash
tiger db save-password <service-id>
```

Enter the password from your configuration file when Tiger CLI asks for it. Tiger CLI and Tiger MCP use the saved password to connect to the database.

In [Tiger Console](https://console.cloud.tigerdata.com/dashboard/services), select your service, click `Operations` > `Environment`, and change the service environment to production. Then show the service's details with this command:

```bash
tiger service get <service-id>
```

Verify the `Environment` row shows `PROD` in the output, which this example trims to its first rows:


</NumberedItem>
<NumberedItem title="Turn on read-only mode for production">

Set the [`read_only`](https://www.tigerdata.com/docs/reference/tiger-cloud/tiger-cli#configuration-options) option to `prod` with this command:

```bash
tiger config set read_only prod
```

With this setting, Tiger CLI and Tiger MCP open read-only database sessions on services tagged `PROD`, and they refuse to stop, resize, or delete those services. Services tagged `DEV` stay writable.

</NumberedItem>
<NumberedItem title="Install Tiger MCP for Claude Code">

Add Tiger MCP to [Claude Code](https://docs.anthropic.com/en/docs/claude-code) with this command:

```bash
tiger mcp install claude-code
```

</NumberedItem>

Open a second terminal in the same directory as the first and start Claude Code with the `claude` command. The agent writes a file to this directory later, and you run that file from the first terminal.

## Find the slow query

<NumberedList>
<NumberedItem title="Repeat a dashboard query (in a third terminal)">

Open a third terminal and start a new `psql` session. Turn on timing and repeat a dashboard query, the ten-year average and highest temperature of `machine1`, every second with this SQL:

```sql
\timing on
SELECT avg(value) AS avg_temperature,
       max(value) AS max_temperature
FROM sensor_data
WHERE device_id = 'machine1'
  AND tag = 'temperature'
\watch 1
```

<NumberedItem title="Check the CPU usage and the logs">

Ask the agent for the service's CPU usage and logs with this prompt:

```text
For service <service-id>, show the CPU usage for the past hour against the service's total CPU, and tell me the average for the past three minutes. Then summarize the service logs for the same hour.
```

Verify the agent reports the CPU usage and summarizes the logs. Note the three-minute average, which you compare with the value after the fix. Example reply, trimmed to the CPU average and the agent's conclusion:

```
CPU on tutorial-db jumped about 50-fold at 18:07 UTC and has stayed there. Even so, the service is using under 6% of its 8 cores. Average over the last three minutes: 468 millicores, 5.9% of total CPU.

The columnstore job's log lines stop at 18:08:15, but CPU has stayed around 465 millicores for 30 minutes since. I checked pg_stat_activity just now: there are no active queries, and every background process is idle. Neither the logs nor the database sessions explain the sustained load.
```

</NumberedItem>
<NumberedItem title="Find the slowest query and its plan">

Ask the agent for the slowest statements and a plan with this prompt:

```text
On service <service-id>, list the five SELECT statements with the highest total execution time in pg_stat_statements. The first one has placeholders in place of its values. Find the same statement in pg_stat_activity to get the values, run EXPLAIN (ANALYZE, BUFFERS) on it, and tell me where it spends its time.
```

Verify the agent names the dashboard query and reports that the query reads every chunk and discards most of the rows it decompresses. Example reply, trimmed to the summary:

```
The top statement is a monitoring query that runs about every 1.2 seconds. Each run reads all 523 chunks of sensor_data, decompresses about 4.4 million rows and throws away 98% of them. It's also the most likely cause of the sustained CPU from the last question.
```

The plan has one branch for each chunk, which is more than the 100 rows the agent's query tool returns, so the agent summarizes the plan.

The columnstore sorts each chunk by time alone, so every compressed batch holds rows from all machines and sensors. The query reads every batch and discards the rows from the other machines and sensors. A [`segmentby`](https://www.tigerdata.com/docs/build/columnar-storage/setup-hypercore) setting groups compressed rows by the columns it names, so a query for one machine and sensor reads only that group.

</NumberedItem>

## Test the fix on a fork

<NumberedList>
<NumberedItem title="Fork the service">

Ask the agent to fork the production service with this prompt:

```text
Fork service <service-id> at its current state, wait until the fork is ready, and tell me the fork's service ID.
```

Verify the agent reports a new service ID, and note it. On the test service, the fork took about two minutes.

Read-only mode allows the fork because Tiger MCP tags a fork `DEV` by default. The agent can write to the fork and still can't write to the production service.

</NumberedItem>
<NumberedItem title="Write the change to a file">

Ask the agent to write the change with this prompt:

```text
Use the setup-timescaledb-hypertables skill to choose segmentby columns for the sensor_data hypertable on service <service-id>, so that the dashboard query reads only the rows it needs. Write the SQL to segmentby.sql. The file must set the new segmentby columns, then convert every chunk to the rowstore and back to the columnstore. Use no transaction control statements. Don't run the file.
```

TimescaleDB applies a new `segmentby` setting only to chunks it converts after the change, which is why the file converts the existing chunks again.

</NumberedItem>
<NumberedItem title="Review the file">

Open `segmentby.sql` and check it against this list.

- It sets `segmentby` on `sensor_data` to `device_id, tag`, the two columns the dashboard query filters on.
- It converts every chunk to the rowstore and back to the columnstore.
- Each call to [`convert_to_rowstore()`](https://www.tigerdata.com/docs/reference/timescaledb/hypercore/convert_to_rowstore) and [`convert_to_columnstore()`](https://www.tigerdata.com/docs/reference/timescaledb/hypercore/convert_to_columnstore) uses only parameters that the reference lists.
- It has no `BEGIN` or `COMMIT`. Tiger CLI and Tiger MCP run a file as one transaction, and a `COMMIT` inside a `DO` block fails there.
- It changes nothing else.

Compare the file with this example:

```sql
ALTER TABLE sensor_data SET (
    tsdb.segmentby = 'device_id, tag'
);

DO $$
DECLARE
    chunk regclass;
BEGIN
    FOR chunk IN SELECT c FROM show_chunks('sensor_data') AS c LOOP
        CALL convert_to_rowstore(chunk);
        CALL convert_to_columnstore(chunk);
    END LOOP;
END
$$;
```

If the file does something else, edit it or ask the agent to correct it. On the test run, the agent's file also set `orderby` to `time DESC`, which the chunks already used.

</NumberedItem>
<NumberedItem title="Run the file on the fork">

Replace `<fork-service-id>` with the fork's service ID and ask the agent to run the file with this prompt:

```text
Run segmentby.sql on the fork <fork-service-id> with a query timeout of 900 seconds.
```

The agent's query tool stops a statement after 30 seconds unless the prompt sets a longer timeout.

Verify the agent reports that both statements completed.

If the run fails, the agent may correct the file and run it again. Review the file again before you continue. On the test run, the first attempt failed on a wrong parameter name, the agent corrected the file, and the second attempt took 14 seconds.

</NumberedItem>
<NumberedItem title="Compare the fork with production">

Ask the agent to compare the two services with this prompt:

```text
Run EXPLAIN (ANALYZE, BUFFERS) on the dashboard query on the fork <fork-service-id> and on service <service-id>. Compare the buffers and the execution time.
```

Verify the agent reports fewer buffers and a shorter execution time on the fork than on production. Example reply, trimmed to the comparison:

```
Comparison, using runs 2 and 3:
- Execution time: about 150 ms on production against about 25 ms on the fork, so the fork is about 6× faster.
- Execution buffers: 38,000 to 40,000 on production against a steady 1,046 on the fork, about 37× fewer. Against run 1's 48,215, it's about 46× fewer.
```

Claude Code can show these tool calls as failed. On the test run, the agent returned its plan summary through a raised error, and nothing failed on either service.

</NumberedItem>
</NumberedList>

## Apply the fix to production

<NumberedList>
<NumberedItem title="Run the file on production (in the first terminal)">

Run `segmentby.sql` on the production service yourself with this command in the first terminal:

```bash
TIGER_READ_ONLY=off tiger db query <service-id> -f segmentby.sql
```

`TIGER_READ_ONLY=off` turns read-only mode off for this one command. The saved `read_only` setting stays `prod`, so the agent still can't write to production.

Verify the output shows both statements completed.

```
ALTER TABLE
DO
```

The file runs as one transaction. On the test service, it took 14 seconds, and the dashboard query waited for it, with its slowest run at 13.3 seconds.

## Troubleshooting

These problems can come up while you follow the tutorial.

- **The agent shows no Tiger MCP tools after the install.** Claude Code loads Tiger MCP when it starts. Quit Claude Code, start it again, and ask it whether the Tiger MCP server is active.
- **An agent write succeeds on your service.** The service still has the `DEV` tag, and `read_only` set to `prod` protects only services tagged `PROD`. Drop the table the agent created, then tag the service as described in [Set up the agent](#set-up-the-agent).
- **The agent can't fork the service.** The `read_only` option has the value `all`, which removes the fork tool from Tiger MCP. Run `tiger config set read_only prod`, then restart Claude Code.
- **Your own `tiger db query` fails as read-only.** The command ran without `TIGER_READ_ONLY=off`, so Tiger CLI opened a read-only session on the service tagged `PROD`. Put `TIGER_READ_ONLY=off` at the start of the same line as the command.
- **The dashboard query stays slow after the change.** Some chunks keep the old setting, because TimescaleDB applies a new `segmentby` setting only to chunks it converts after the change. Find the chunks with no `segmentby` value in [`timescaledb_information.chunk_columnstore_settings`](https://www.tigerdata.com/docs/reference/timescaledb/hypercore/chunk_columnstore_settings), and convert them to the rowstore and back to the columnstore, as `segmentby.sql` does.

## Recap

In this tutorial, you found a slow query on a production service with an AI agent that could only read it, tested a fix on a fork, and applied the fix yourself. Use this table as a reference for each stage.

| Section | Technique | Why it matters |
|---|---|---|
| Set up the agent | A `PROD` tag on the service and `read_only` set to `prod` | The agent reads production and can't write to it |
| Find the slow query | Service metrics, logs, `pg_stat_statements`, and a query plan, all from prompts | The diagnosis needs no write access |
| Test the fix on a fork | A fork tagged `DEV` | The agent runs the change on a copy of production's data |
| Apply the fix to production | A reviewed file and `TIGER_READ_ONLY=off` on one command | You make the production write, and the saved setting stays in place |

These measurements were collected from a test Tiger Cloud service with 8 CPUs and 32 GiB of memory, running PostgreSQL 18.7 and TimescaleDB 2.32.1, with Tiger CLI 0.30.0 and Claude Code 2.1.332. Buffers count 8 KB blocks read from memory and disk, and millicores are thousandths of one CPU.

| Measurement | Before | After | Change |
|---|---|---|---|
| Dashboard query execution time | 151.9 ms | 31.0 ms | 4.9 times shorter |
| Dashboard query buffers | 48,215 | 1,046 | 46 times fewer |
| Service CPU usage | 465 millicores | 90 millicores | 5.1 times lower |

Query times are the execution time that `EXPLAIN ANALYZE` reports, as the median of five runs. CPU usage is the three-minute average while one dashboard query repeated every second.

Before the fix, every refresh of the dashboard panel read 48,215 buffers to return one row. After the fix, the same refresh reads 1,046 buffers. Each added panel or viewer repeats the query, so the saving grows with the number of dashboards that read the table.

The time each run takes in `psql` fell less, from a median of 213 ms to 94 ms. Planning for 523 chunks takes about 50 ms of every run, and the fix leaves it unchanged. A time filter on the query reduces the planning time, as [Diagnose and fix a slow hypertable query](https://www.tigerdata.com/docs/learn/tutorials/diagnose-and-fix-a-slow-hypertable-query) shows.

You made every write to the production service yourself. You loaded the data and converted the chunks from `psql`, and you ran `segmentby.sql` with Tiger CLI. The agent's only writes went to the fork. The same sequence of a read-only diagnosis, a fork, a reviewed file, and your own write also works for other changes, such as a new index or a retention policy.

For your next step, tag one of your own production services `PROD`, set `read_only` to `prod`, and give the agent the prompts from [Find the slow query](#find-the-slow-query). The prompts only read from the service, so they are safe to run against production.
